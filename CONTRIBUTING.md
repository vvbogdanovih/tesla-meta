# Внесок у документацію

Цей репозиторій — мета-репо проєкту **Tesla Lviv**: тут живе лише документація та координація. Код застосунків — в окремих репозиторіях (див. [README](README.md#структура-проєкту)).

## Структура

```
tesla-meta/
├── README.md           точка входу в проєкт
├── CONTRIBUTING.md     цей файл
├── LICENSE             умови використання
└── docs/
    ├── README.md       індекс документації
    ├── PRD.md          product requirements
    ├── FRD.md          functional requirements
    ├── adr/            architecture decision records
    └── assets/         діаграми та медіа
```

## Конвенції документів

- Мова документації — **українська**.
- Формат — **Markdown** (GitHub-flavored).
- Іменування файлів — короткі, без зайвих суфіксів: `PRD.md`, `FRD.md` (не `PRD_TeslaLviv.md`).
- Кожен документ має шапку: версія, дата (`ДД.ММ.РРРР`), статус (`Draft` / `Review` / `Approved`).
- Внутрішні посилання — **відносні** (`docs/PRD.md`, `FRD.md`), щоб не ламались при перегляді в GitHub та локально.
- Діаграми робити в **[Mermaid](https://mermaid.js.org/)** прямо в Markdown (блок ` ```mermaid `), а не картинками — вони версіонуються в git, рендеряться в GitHub і легко правляться. Растрові зображення/скриншоти складати в `docs/assets/` і посилатися відносним шляхом лише коли Mermaid не підходить.

  Приклад:

  ````markdown
  ```mermaid
  flowchart LR
    Web[Next.js] -->|REST| API[NestJS] --> DB[(MongoDB)]
    API --> S3[(S3)]
  ```
  ````

## Версіонування

- Версію документа піднімати в його шапці при змістовних змінах:
  - **patch** (1.0 → 1.0.1) — виправлення, уточнення формулювань;
  - **minor** (1.0 → 1.1) — нові розділи/вимоги без зміни напрямку;
  - **major** (1.x → 2.0) — суттєвий перегляд scope чи архітектури.
- Дату в шапці оновлювати разом із версією.

## Архітектурні рішення (ADR)

Будь-яке значуще технічне рішення (вибір БД, платіжного шлюзу, підходу до міграції тощо) фіксувати окремим ADR у [`docs/adr/`](docs/adr/) за [шаблоном](docs/adr/0000-template.md). Назва файлу: `NNNN-короткий-заголовок.md` (порядковий номер).

## Робота через гілки

1. Зміни вносити в окремій гілці (`docs/<тема>`, `adr/<тема>`).
2. Один PR — одна логічна зміна.
3. У PR коротко описати **що** і **навіщо** змінено (шаблон підставиться автоматично).
