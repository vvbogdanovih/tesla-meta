# ADR-0013: Order — статус/методи оплати й доставки та пошук контактів як окремі колонки

- **Статус:** Accepted
- **Дата:** 02.07.2026
- **Автори:** —

## Контекст

`Order` зберігає `customer / delivery / payment` як JSONB-снапшоти замовлення на момент покупки (за аналогією зі знімком позицій в `OrderItem`). Це доречно для незмінних даних без зовнішніх звʼязків.

Проблема — усередині цих JSON лежать **структуровані, запитувані** дані:

- `payment.status` (`pending → paid → …`) — **змінний lifecycle-стан**, а не снапшот: оновлюється адміном/вебхуком провайдера й фільтрується в адмінці («показати всі неоплачені»). Зберігання в JSON означає оновлення через read-modify-write усього обʼєкта та відсутність індексу.
- `payment.method`, `delivery.method` — перелічувані виміри для звітів (enum-и `PaymentMethod` / `DeliveryMethod` вже оголошені у схемі; `DeliveryMethod` уже є колонкою в `Address`).
- `customer.phone / email` — типові цілі пошуку замовлень в адмінці; по JSON без індексу це повільно.

## Розглянуті варіанти

- **A. Лишити все в JSON.** Мінімум змін, але змінний статус без індексу, незручні фільтри/звіти, пошук за контактом — full scan.
- **B. Винести все в нормалізовані таблиці.** Надлишково: адреса/деталі — справжній снапшот, звʼязки не потрібні.
- **C. Гібрид (обрано).** Змінний статус і перелічувані методи → колонки-enum з індексом; пошук за контактом → trigram GIN на JSON-виразі; решта снапшоту (імʼя, місто, відділення, канал-деталі) лишається в JSONB.

## Рішення

Варіант **C**. У моделі `Order`:

- `paymentStatus PaymentStatus @default(pending)` + `@@index([paymentStatus])`;
- `paymentMethod PaymentMethod`, `deliveryMethod DeliveryMethod` (обовʼязкові, незмінні);
- пошук за контактом — trigram GIN на виразах `customer->>'phone'` / `customer->>'email'` (raw-міграція, як для `pg_trgm` каталогу).

JSONB `customer` / `delivery` лишається **джерелом снапшоту** (незмінні дані, що ніде не фільтруються). `paymentStatus`/`method`-и — **джерело правди** для статусу й фільтрів. Колонку `payment` (jsonb) **прибрано**: після винесення method/status вона ставала порожньою (`{}`); канал-специфічні деталі провайдера (напр. id транзакції LiqPay) додамо окремою колонкою тоді, коли зʼявиться інтеграція. Форма відповіді API не змінюється: вкладені `payment.{method,status}` та `delivery.method` **композяться з колонок** у сервісі — фронтенд і адмінка правок не потребують.

## Наслідки

- Позитивні: індексований фільтр за статусом оплати; звіти за методами; швидкий пошук замовлень за телефоном/email; статус оновлюється атомарним `UPDATE` однієї колонки без ризику розсинхрону JSON.
- Негативні / компроміси: потрібна міграція з **бекфілом наявних рядків** зі снапшоту JSON; старі ключі `status`/`method` прибрано з JSON окремою міграцією (щоб не було дубля-джерела); колонку `payment` (jsonb) видалено як порожню.
- Що змінює у [FRD](../FRD.md): FR-A4 — фільтр за статусом оплати та пошук замовлень за контактом; таблиця API `/api/orders` отримує параметр `paymentStatus`. У [db-schema](../db-schema.md) — оновлено модель `Order` та розділ індексів.
