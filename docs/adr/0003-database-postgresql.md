# ADR-0003: PostgreSQL замість MongoDB

- **Статус:** Accepted
- **Дата:** 27.06.2026
- **Автори:** команда проєкту
- **Пов'язано:** [ADR-0002](0002-catalog-compatibility-architecture.md)

## Контекст

Початковий стек (PRD/FRD v1.x) передбачав **MongoDB**. Проте архітектура каталогу з [ADR-0002](0002-catalog-compatibility-architecture.md) — нормалізований довідник авто, **M2M-сумісність** (`product_fitment`), покоління з діапазонами дат, замовлення/оплати з транзакціями, фасетна фільтрація і майбутній VIN-підбір — за своєю природою **реляційна**.

У документній БД це доводиться емулювати (масиви id у документі товару), втрачаючи цілісність і зручність запитів типу «всі товари, сумісні з авто X покоління Y».

## Розглянуті варіанти

- **PostgreSQL** — реляційна, FK-цілісність, потужні індекси/запити, транзакції, JSONB для гнучких атрибутів, розширення (full-text, pg_trgm для пошуку).
- **MySQL/MariaDB** — теж реляційна, простіша/поширена, але слабша за Postgres у JSON, індексах і розширеннях.
- **MongoDB (статус-кво)** — гнучка схема, але слабка для M2M-цілісності, JOIN-ів і складних вибірок сумісності.

## Рішення

Обрано **PostgreSQL**.

- Природні зв'язки `cars` ↔ `product_fitment` ↔ `products` ↔ `systems` з foreign keys.
- Транзакції для замовлень/оплат.
- Фасетна фільтрація з індексами; full-text/`pg_trgm` для пошуку за назвою та артикулом.
- **JSONB** для гнучких характеристик товару (`attributes`) — там, де потрібна документна гнучкість.
- ORM: Prisma або TypeORM у звʼязці з NestJS.

## Наслідки

- ✅ Цілісність і прості потужні запити сумісності; готовність до VIN.
- ✅ Один canonical-товар (узгоджено з ADR-0002).
- ⚠️ **Зміна стеку** відносно FRD: оновити стек у README, PRD, FRD (§1, §6, §7).
- ⚠️ Міграція з WooCommerce (MySQL) → PostgreSQL: ETL зі злиттям товарів за артикулом і побудовою `product_fitment`.
