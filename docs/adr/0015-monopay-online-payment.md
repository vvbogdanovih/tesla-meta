# ADR-0015: Онлайн-оплата карткою через monopay (Monobank acquiring)

- **Статус:** Accepted
- **Дата:** 05.07.2026
- **Автори:** —

## Контекст

Крім наявних способів оплати (накладений платіж, IBAN-переказ, готівка при самовивозі — ADR-0013) потрібна **онлайн-оплата карткою** прямо на сайті: Visa/Mastercard, Apple Pay, Google Pay. Провайдер — **Monobank acquiring (monopay)**: створюємо інвойс, ведемо клієнта на сторінку оплати monobank, повертаємо назад і фіксуємо статус.

Обмеження та передумови:

- Токен еквайрингу (`X-Token`) — секрет продавця. Реквізити продавця вже зберігаються в БД зашифрованими і керуються superadmin (ADR-0008). Логічно тримати monopay-токен там само, а не в env (зміна токена без редеплою, консистентність із LiqPay/IBAN).
- Enum `PaymentMethod` уже має значення `card` (лейбл «Картка онлайн»). Другий провайдер (LiqPay) теоретично можливий — метод оплати не має бути привʼязаний до конкретного провайдера.
- Статус оплати вже винесено в колонку `Order.paymentStatus` (ADR-0013) з ручним керуванням в адмінці. Онлайн-оплата має оновлювати **той самий** статус, не створюючи паралельний механізм.
- Вебхук потребує перевірки підпису; у dev публічного URL для колбека може не бути.

## Розглянуті варіанти

**Зберігання токена**
- **A. env `MONOBANK_API_KEY`** — просто, але зміна токена = редеплой; розходиться з ADR-0008.
- **B. У БД, канал `PaymentRequisite.monopayToken` (обрано)** — зашифровано (AES-256-GCM), керує superadmin в адмінці, консистентно з IBAN/LiqPay.

**Метод оплати**
- **A. Нове enum-значення `monopay`** — міграція enum, дублює семантику «картка».
- **B. Повторно використати `card` (обрано)** — monopay є *провайдером* методу «Картка онлайн». Бекенд обирає активний monopay-реквізит. Додати LiqPay пізніше — без зміни методу.

**Фіксація статусу**
- Вебхук `POST /api/payments/monopay/webhook` з перевіркою підпису `X-Sign` (ECDSA SHA-256, публічний ключ із `GET /api/merchant/pubkey`) — основний канал.
- **Поллінг-fallback** `GET /api/payments/monopay/status/:orderNumber` — сторінка успіху звіряє статус, поки `pending`. Покриває dev без публічного URL і пропущені колбеки.

## Рішення

1. **Токен** — `PaymentRequisite.monopayToken` (зашифровано) + `monopayActive`; активним по каналу monopay може бути один запис. Розшифрований токен живе лише в межах виклику сервісу, не логується, назовні не віддається (лише прапорець `monopayTokenSet`).
2. **Метод** — `PaymentMethod.card` = онлайн-оплата через активний monopay-реквізит.
3. **Потік**: чекаут із `paymentMethod=card` → створення замовлення → інвойс monopay (сума з `Order.total` у копійках — **authoritative**) → редірект на `pageUrl` → оплата → `redirectUrl` повертає на `/order/{number}/success` → статус із вебхука або поллінгу.
4. **`Order.paymentInvoiceId`** — нова колонка (+індекс) для звірки статусу і привʼязки вебхука до замовлення.
5. **Env** — додано опційний `API_PUBLIC_URL` (для `webHookUrl`); без нього інвойс створюється без вебхука (лише поллінг). Мертві `PAYMENT_PROVIDER/PUBLIC_KEY/PRIVATE_KEY` прибрано.
6. **Ідемпотентність** — оновлення статусу за `invoiceId` безпечне до повторів; не понижає `paid` пізнім `failed`; `success→paid`, `failure|expired→failed`, `reversed→refunded`, `created|processing|hold→pending`.

## Наслідки

- Позитивні: онлайн-оплата без редеплою для зміни токена; статус оновлюється автоматично, ручний перезапис адміна (ADR-0013) лишається; dev працює без тунеля (поллінг).
- Негативні / компроміси: залежність від доступності monobank API; вебхук потребує raw body (`rawBody: true` у Nest) — окремий шлях парсингу; `basketOrder[].sum` (чек) потребує звірки при живому тесті — на факт оплати не впливає (сума в `amount`).
- Зміни у [FRD](../FRD.md) — розділ оплати; у [db-schema](../db-schema.md) — колонка `payment_invoice_id`; у [backend-architecture](../backend-architecture.md) — модуль `payments`.
