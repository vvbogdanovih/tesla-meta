# ADR-0005: Порядок реалізації — спершу адмінка, потім клієнтський застосунок

- **Статус:** Accepted
- **Дата:** 27.06.2026
- **Автори:** команда проєкту
- **Пов'язано:** [ADR-0002](0002-catalog-compatibility-architecture.md) · [ADR-0003](0003-database-postgresql.md) · [ADR-0004](0004-admin-separate-app-and-roles.md) · [модель БД](../db-schema.md)

## Контекст

Маємо чотири складові: `tesla-api` (NestJS + PostgreSQL), `tesla-admin` (Next.js), `tesla-web` (Next.js), `tesla-meta` (документація). Потрібно визначити **послідовність реалізації**.

Клієнтський сайт нічого не показує без наповнених даних: товарів, **довідника авто** (`cars`), систем і **сумісності** (`product_fitment`). Ці дані вводяться/мігруються **через адмінку**. Отже, сторфронт залежить від адмінки й заповненої БД.

## Рішення

Реалізовувати в такому порядку:

1. **БД (PostgreSQL) + схема** — фундамент (вже змодельовано, [db-schema.md](../db-schema.md)).
2. **`tesla-api` (NestJS)** — моделі, міграції, auth/RBAC, CRUD-ендпоінти каталогу/сумісності/замовлень.
3. **`tesla-admin` (Next.js)** — керування даними: довідник авто, системи, товари з сумісністю, замовлення, ліди, контент; ETL-міграція з WooCommerce (дедуплікація за артикулом, побудова `product_fitment`).
4. **`tesla-web` (Next.js)** — клієнтський застосунок поверх уже наповненої БД і готового API.

Тобто **спершу адмінка** (разом із БД/API), **потім юзер-апка**.

## Обґрунтування

- Сторфронт безглуздо будувати без даних; адмінка — інструмент їх внести/мігрувати.
- Адмінка змушує раніше стабілізувати **модель даних і API-контракти**, на які потім спирається `tesla-web`.
- Можна почати **міграцію 1000+ SKU** і наповнення довідника авто паралельно з розробкою сторфронту.
- API-first: обидва фронти споживають один контракт (ADR-0004).

## Наслідки

- ✅ До старту `tesla-web` БД вже наповнена реальними товарами/сумісністю — реальне тестування фільтрів/пошуку.
- ✅ Чіткі контракти API фіксуються на етапі адмінки.
- ⚠️ Бізнес-цінність для кінцевого покупця з'являється пізніше (сторфронт — останній) — компенсується тим, що дані/міграція готуються заздалегідь.
- ⚠️ Дизайн обох фронтів робимо паралельно (вже є), але **реалізація** — послідовна.
- 🔗 Уточнює фази в [PRD §9](../PRD.md) (порядок збірки в межах MVP).
