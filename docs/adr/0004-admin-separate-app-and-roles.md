# ADR-0004: Адмінка — окремий Next.js застосунок; ролі User / Admin / SuperAdmin

- **Статус:** Accepted
- **Дата:** 27.06.2026
- **Автори:** команда проєкту

## Контекст

Потрібна адмін-панель для керування товарами, сумісністю, замовленнями, лідами, контентом (FRD §4). Питання — чи вбудовувати її в клієнтський застосунок, чи виносити окремо; і яку рольову модель прийняти.

## Рішення

1. **Адмінка — окремий застосунок** на **Next.js** (окремий репозиторій `tesla-admin`), що споживає **той самий NestJS API**, що й клієнтський сайт.

2. **Рольова модель — три ролі:**
   - **User** — звичайний користувач/покупець (особистий кабінет, замовлення).
   - **Admin** — керування каталогом, товарами/сумісністю, замовленнями, лідами, контентом, банерами.
   - **SuperAdmin** — усе вищеназване + керування адмінами, ролями та системними налаштуваннями.

## Наслідки

- ✅ **Розділення доменів:** публічний сайт і адмінка деплояться/масштабуються/захищаються незалежно; адмінка може бути за окремим доменом/VPN, не впливає на SEO/розмір клієнтського бандла.
- ✅ **Спільний бекенд:** одна правда даних і бізнес-логіки в NestJS API; адмінка та сайт — два фронти.
- ✅ **Безпека:** admin/superadmin-ендпоінти захищені на рівні API (RBAC за роллю в JWT), незалежно від фронту.
- ✅ Проста, зрозуміла рольова модель (3 ролі) замість дробленої.
- ⚠️ Дублювання частини UI-інфраструктури (дизайн-токени, компоненти) між `tesla-frontend` і `tesla-admin` — мітигація: спільний пакет UI/токенів за потреби.
- 🔗 Впливає на: структуру репозиторіїв ([README](../../README.md)), [FRD §1, §4](../FRD.md), [модель БД](../db-schema.md) (`user_role`).
