# ADR-0010: Єдина сутність User + роль (без розділення профілів)

- **Статус:** Accepted
- **Дата:** 29.06.2026
- **Автори:** команда проєкту
- **Пов'язано:** [ADR-0004](0004-admin-separate-app-and-roles.md) · [db-schema.md](../db-schema.md)

## Контекст

Постало питання, чи розділити адмінів і клієнтів на окремі сутності/профілі (базовий `User` + окремі профілі), чи лишити одну таблицю `User` з полем `role`. Адмін — фактично «урізаний» користувач: йому не потрібні адреси/замовлення/кошик, лише ідентичність і права.

## Рішення

Лишаємо **єдину сутність `User` + `role`** (`user | admin | superadmin`).

- Клієнтські дані (адреси, замовлення, кошик, ліди) — звʼязки на `User`; для адмінів просто порожні.
- **Не** вводимо окремі таблиці `Admin`/`Customer` і не виносимо `CustomerProfile`.

Розглянуті альтернативи: 1:1 `CustomerProfile`; повністю окремі таблиці з роздільною автентифікацією — відхилено як надлишкові для масштабу одного магазину.

## Наслідки

- ✅ Проста автентифікація (одна точка), мінімум JOIN-ів, RBAC за роллю (узгоджено з [ADR-0004](0004-admin-separate-app-and-roles.md)).
- ⚠️ Рядки адмінів мають незадіяні клієнтські звʼязки — косметично.
- Якщо клієнтський профіль суттєво розростеться (бонуси, згоди, програми лояльності) — повернутись до виділення `CustomerProfile` (новий ADR).
