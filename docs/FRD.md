## 1. Архітектура (огляд)

```
[tesla-frontend · Next.js (SSR/ISR)] ─┐
                                 ├─REST──> [tesla-backend · NestJS] ──> [PostgreSQL]
[tesla-admin · Next.js (RBAC)] ──┘                 │
                                                   ├──> [S3] (зображення товарів, OG)
                                                   ├──> [Платіжний шлюз] (еквайринг Visa/MC)
                                                   ├──> [Нова Пошта API] (відділення/доставка)
                                                   └──> [Email/SMS сервіс] (нотифікації, заявки)
```

- **Два фронти, спільний бекенд** (ADR-0004): публічний сайт `tesla-frontend` і адмінка `tesla-admin` — окремі Next.js застосунки на одному NestJS API.

- **Next.js** — рендеринг сторінок (SSR для SEO-критичних, ISR для каталогу/товарів), клієнтська інтерактивність, кошик.
- **NestJS** — REST API: товари, сумісність/довідник авто, категорії, кошик, обране, замовлення, користувачі, ліди, контент. ORM: **Prisma**.
- **PostgreSQL** — реляційне сховище: довідник авто, M2M-сумісність, товари, замовлення (схема в §7). JSONB для гнучких атрибутів.
- **S3** — зберігання та роздача зображень (з CDN), генерація OG-зображень.

## 3. Функціональні вимоги по компонентах

### 3.1 Хедер (наскрізний)
- **FR-H1:** Логотип-посилання на головну.
- **FR-H2:** Головне меню: Магазин, Про нас, Контакти.
- **FR-H3:** Рядок пошуку з автодоповненням (за назвою та артикулом) — *нове*.
- **FR-H4:** Іконка кошика з лічильником товарів і dropdown-прев'ю.
- **FR-H4a [НОВЕ]:** Іконка «Обране» (♡) з лічильником позицій; клік → `/wishlist` (авторизований) або перехід на логін (гість) ([ADR-0012](adr/0012-wishlist-auth-crm.md)).
- **FR-H5:** Вхід в особистий кабінет / іконка користувача.
- **FR-H6:** Мобільне бургер-меню.

### 3.2 Головна сторінка (P1)
- **FR-1.1:** Банер/слайдер (керований з адмінки).
- **FR-1.2:** Блок «Обрати модель» — картки **усіх 6 категорій моделей** (Model 3, Model Y, Model S, Model X, Model 3 Highland, Model Y Juniper) з переходом у каталог категорії. *(Виправлення: поточний сайт показує лише 4 — Highland і Juniper недоступні з головної.)*
- **FR-1.3:** Блок «Популярні товари» / «Новинки» — грід карток товару.
- **FR-1.4:** Блок «Блог» — 3 останні статті.
- **FR-1.5:** Форма «Залишіть заявку на підбір» (Ім'я, Телефон, VIN, опис).

### 3.3 Каталог: сторінка моделі / модель × категорія (P3, P4)
- **FR-2.1:** Заголовок категорії + лічильник `Показано X–Y із Z`.
- **FR-2.2:** Грід карток товару, пагінація (12/24/48 на сторінку, конфігуровано).
- **FR-2.3:** Сайдбар навігації: модель авто (фільтр сумісності) → категорії (глобальні). *(Модель — не власник товару, а фільтр сумісності — ADR-0002.)*
- **FR-2.4 [НОВЕ]:** Панель фасетних фільтрів:
  - **Модель/покоління авто** (сумісність, multi-select — товар може підходити до кількох)
  - Стан: Новий / Б/у / Уцінка
  - Тип: Оригінал / Аналог
  - Наявність: В наявності / під замовлення
  - Діапазон ціни (slider, мін–макс)
  - Категорія
- **FR-2.5:** Сортування: за замовчуванням / популярністю / новизною / ціна ↑ / ціна ↓.
- **FR-2.6:** Фільтри відображаються в URL (shareable, SSR-friendly): `?type=original&inStock=true&minPrice=...`.
- **FR-2.7:** Хлібні крихти.

### 3.3a Прайс-лист / табличний каталог (P2a)

> Щільний **табличний** перегляд каталогу поруч зі сіткою карток (референс: `fillando.com/price-sheet`). Окрема сторінка `/price-sheet`; той самий бекенд-ендпоінт, що й каталог ([ADR-0011](adr/0011-price-sheet-table-view.md)).

- **FR-2.8 [НОВЕ]:** Таблиця товарів із колонками: **Фото · Назва** (+ індикатор наявності) **· Артикул · Категорія · Сумісність · Тип · Стан · Ціна** (+ закреслена стара, якщо `onSale`) **· Наявність** (`stockQty`) **· «У кошик»**. «Сумісність» — перелік сумісних моделей, обрізаний (напр. `Model 3, Model Y +2`); Тип/Стан — бейджі (Новий не показуємо).
- **FR-2.9:** Ті самі фасетні фільтри (FR-2.4) у сайдбарі + текстовий пошук за назвою/артикулом; стан фільтрів у URL (shareable, SSR-friendly).
- **FR-2.10:** **Нескінченний скрол** (підвантаження по 50; `IntersectionObserver`), футер «Показано N із Z», стани завантаження/помилки/порожнього результату.
- **FR-2.11:** Сортування за замовчуванням — **спочатку в наявності** (`stockQty > 0`), далі за назвою; доступний той самий сорт-дропдаун, що й у каталозі (FR-2.5).
- **FR-2.12:** Респонсив — таблиця зі sticky-заголовком на десктопі, картковий список на мобільному.
- **FR-2.13:** Додавання в кошик по рядку (компактна дія, спільний стор кошика).
- *Колонки виробник/матеріал/колір і «Синхронізовано» з референсу Fillando **не переносяться** (специфіка філаменту / зовнішньої синхронізації).*

### 3.4 Картка товару (P5)

> Більшість елементів картки **вже реалізовано** на поточному сайті (галерея ~7 фото, SKU, бейджі Новий/Оригінал/Аналог, стара/нова ціна, «Купити в 1 клік», «Схожі товари»). Завдання — зберегти функціонал і покращити верстку/UX/продуктивність, а не будувати з нуля.

- **FR-3.1:** Галерея зображень (до 10+) з мініатюрами та зумом/лайтбоксом.
- **FR-3.1a:** **«Живі фото товару»** — окремий блок під галереєю, **перед описом**: реальні знімки саме цього екземпляра («як на складі», без ретуші) як сигнал довіри. Візуально відокремлений від студійної галереї (акцентна смуга-довіри, іконка камери, бейдж «реальні знімки», горизонтальний скрол, клік → лайтбокс). Зберігаються в тій самій сутності, що й галерея, з прапорцем `isLive` ([db-schema](db-schema.md) · `ProductImage.isLive`); завантажуються **окремою секцією в адмінці**. Блок рендериться **лише за наявності** живих фото (інакше відсутній). Включаються в `Product.image[]` JSON-LD (FR-3.12). На **картці товару** (каталог, «схожі») за наявності живих фото показується плашка-сигнал (іконка камери + «Живі фото»); каталог віддає прапорець `hasLivePhotos` без завантаження самих фото.
- **FR-3.2:** Бейджі: Стан (Новий / Б/у / Уцінка), Тип (Оригінал/Аналог), Наявність. *Наявність визначається з `stockQty` (>0 — в наявності); окремого прапорця немає.*
- **FR-3.3:** Назва, артикул (код запчастини), категорія (одна, глобальна — без ієрархії); **«Сумісність» — список усіх сумісних моделей/поколінь** (а не одна модель), напр. «Підходить до: Model 3, Model Y, Model 3 Highland».
- **FR-3.4:** Ціна: поточна + закреслена стара + % знижки. *Стара ціна показується лише коли увімкнено прапорець знижки `onSale`.*
- **FR-3.5:** Лічильник кількості + «Додати в кошик».
- **FR-3.6:** «Купити в 1 клік» — модалка з мін. полями (Ім'я, Телефон).
- **FR-3.7:** Таблиця характеристик: фіксовані (Стан, Сумісність, Код запчастини, Тип, Категорія) + **довільні `attributes`** (ключ–значення, напр. «Сторона: ліва»).
- **FR-3.8:** Спадні блоки (accordion): Гарантія, Умови доставки та оплати — **беруться з глобальних `ContentBlock`** ([ADR-0009](adr/0009-content-blocks.md)), а не з полів товару.
- **FR-3.9 [Фаза 2]:** «Знайшли дешевше?» — модалка (Ім'я, Телефон, посилання).
- **FR-3.10 [Фаза 2]:** «Підписка на зміну ціни» — модалка (бажана ціна + контакт).
- **FR-3.11:** Блок «Схожі товари».
- **FR-3.12:** Product schema (JSON-LD) для SEO.

### 3.5 Пошук (P6, FR-H3)

> Базовий пошук на поточному сайті вже існує (стандартний WooCommerce), але без автодоповнення й без гарантованого покриття за артикулом. Завдання — **підняти якість**, а не вводити пошук уперше.

- **FR-4.1:** Пошук за назвою товару **та артикулом** (SKU «Код запчастини») — надійне покриття обох.
- **FR-4.2:** Автодоповнення (dropdown із топ-результатами) під час набору.
- **FR-4.3:** Сторінка результатів з тими ж фільтрами/сортуванням, що й каталог.
- **FR-4.4:** Обробка «нічого не знайдено» + пропозиція форми підбору.

### 3.6 Кошик (P7)
- **FR-5.1:** Список позицій: фото, назва, артикул, ціна, кількість (зміна/видалення).
- **FR-5.2:** Підрахунок суми, кількості, знижок.
- **FR-5.3:** Кнопка «Оформити замовлення».
- **FR-5.4:** Збереження кошика (localStorage для гостя + БД для авторизованого).
- **FR-5.5:** Стан порожнього кошика.

### 3.7 Оформлення замовлення (P8)
- **FR-6.1:** Форма: ПІБ, телефон, email.
- **FR-6.2:** Доставка: Нова Пошта / Укрпошта / **самовивіз**, вибір міста + відділення.
- **FR-6.2a [НОВЕ]:** Для **Нової Пошти** — автопідказки при вводі: combobox міста → перемикач **Відділення / Поштомат** → combobox відділення/поштомата. Дані — з локального дзеркала довідника НП (не з АПІ на кожен запит), пошук trigram ([ADR-0014](adr/0014-nova-poshta-directory-mirror.md)). У снапшот замовлення зберігаються `cityRef`/`warehouseRef`/`warehouseType` (для майбутнього ТТН). Укрпошта — поки вільний текст.
- **FR-6.3:** Оплата (enum `PaymentMethod`): **онлайн карткою — monopay** (`card`) / накладений платіж (`cod`) / **за реквізитами IBAN** (`iban`) / **готівка — лише самовивіз** (`cash`). Реквізити отримувача та токен monopay — у `PaymentRequisite`; 3 канали (IBAN/LiqPay/Monopay), активний — один на канал ([ADR-0008](adr/0008-payment-requisites-channels.md)).
- **FR-6.3a [НОВЕ]:** Онлайн-оплата карткою — провайдер **monopay (Monobank acquiring)** ([ADR-0015](adr/0015-monopay-online-payment.md)). При `card` бекенд створює інвойс і повертає `paymentUrl` → редірект на сторінку monopay → після оплати повернення на `/order/{n}/success`. Статус (`paymentStatus`) оновлюється **вебхуком** (`X-Sign`) або **поллінгом** зі сторінки успіху; кнопка «Перейти до оплати / Спробувати ще раз» для несплачених. LiqPay можливий як другий провайдер того самого методу.
- **FR-6.4:** Можливість оформити без реєстрації (гостьовий checkout).
- **FR-6.4a [НОВЕ]:** **Збережені адреси доставки** — лише для авторизованих (модель `Address`, [ADR-0017](adr/0017-saved-delivery-addresses.md)). У checkout: якщо є ≥1 збережена адреса — зверху список **карток-радіо** (default вибрана одразу) + картка «＋ Нова адреса»; вибір картки заповнює форму. Форма нової адреси = той самий combobox-флоу НП (FR-6.2a) + чекбокс **«Зберегти в профіль»** (для залогінених; увімкнений, коли адрес ще немає — перша стає основною). Гість — звичайна форма без збереження + м'який нудж «Увійдіть, щоб зберегти адресу» (не блокер). Адреса зберігає й НП-референси (`cityRef`/`warehouseRef`/`warehouseType`) для відновлення combobox і майбутнього ТТН. Снапшот `Order.delivery` лишається незалежним від `Address` (ADR-0013) — видалення адреси не впливає на замовлення.
- **FR-6.5:** Підтвердження → лист на email + статус замовлення.
- **FR-6.6:** Валідація всіх полів, обробка помилок платежу.

### 3.8 Акаунт (P10–P12)
- **FR-7.1:** Реєстрація (email/телефон + пароль) і логін; JWT-сесії.
- **FR-7.2:** Профіль: контактні дані, **адреси доставки** — розділ «Адреси доставки» з CRUD (додати / редагувати / видалити / зробити основною), картки з `label` + місто/відділення + отримувач ([ADR-0017](adr/0017-saved-delivery-addresses.md)).
- **FR-7.3:** Історія замовлень зі статусами (новий, в обробці, відправлено, виконано, скасовано).
- **FR-7.4:** Деталі замовлення з повторним замовленням.
- **FR-7.5:** Відновлення пароля.

### 3.8a Обране / список бажань (P11a)

> **Лише для авторизованих** ([ADR-0012](adr/0012-wishlist-auth-crm.md)): користувач лайкає товари (♡), щоб повернутись і купити пізніше. Кожен лайк привʼязаний до `User` → адмін бачить попит і контакт для дзвінка (§4, FR-A5a). Обране ≠ кошик: це «зберегти на потім», а не «готовий купити». **Фаза 2** (потребує входу).

- **FR-W1:** ♡-тумблер на **картці товару** (каталог, рядок прайс-листа, «схожі товари») і на **сторінці товару**; активний стан = товар у обраному. Оптимістичний UI + тост.
- **FR-W2:** Гість — ♡ веде на логін/реєстрацію («Увійдіть, щоб зберегти в обране»); обране доступне лише авторизованим ([ADR-0012](adr/0012-wishlist-auth-crm.md)).
- **FR-W3:** Сторінка `/wishlist` — грід карток обраних товарів (той самий `ProductCard`), лічильник, **порожній стан** із CTA у каталог.
- **FR-W4:** Дії у списку: «У кошик» по картці (спільний стор кошика), видалити з обраного (♡ off).
- **FR-W5:** Лічильник у хедері (♡ badge, FR-H4a) — кількість позицій; синхронізується зі стором обраного.
- **FR-W6:** Ідемпотентність — повторне додавання не дублює (toggle). Сторінка `/wishlist` — **`noindex`** (приватні дані користувача).
- *Розширення (поза базовим обсягом): «Усе в кошик», dropdown-прев'ю з хедера, звʼязок із «Підпискою на зміну ціни» (FR-3.10), кілька списків, шеринг за посиланням — подальші ітерації.*

### 3.9 Лід-форми (наскрізні)

**Лід** — заявка-звернення з контактами клієнта (не замовлення), сигнал менеджеру передзвонити/допомогти. Усі зберігаються в таблиці `leads` і доступні в адмінці (розділ **«Ліди»**) зі статусом *new → handled*. Реалізовано: публічний `POST /leads`; admin `GET /leads?status=`, `PATCH /leads/:id` (статус), `DELETE`.

**Типи (`LeadType`):**

| Тип | Назва на сайті | Призначення | Де кнопка | Специфічні поля |
|---|---|---|---|---|
| `fitment` | «Залишити заявку» / Підбір | Клієнт не знайшов деталь — підбір за VIN/кодом | Головна (CTA); згодом «нічого не знайдено» | `vin`, `message` |
| `contact` | «Купити в 1 клік» | Швидка покупка без повного чекауту; загальний контакт | Картка товару | `productId`, `message` |
| `price_match` | «Знайшли дешевше?» | Прохання підлаштувати ціну | Картка товару *(Фаза 2)* | `link`, `productId` |
| `price_subscribe` | «Підписка на зміну ціни» | Сповістити, коли ціна впаде до бажаної | Картка товару *(Фаза 2)* | `targetPrice`, `productId` |

- **FR-8.1:** Обовʼязкові поля — **імʼя + телефон**; решта залежить від типу. Прив'язка до товару (`productId`) для заявок із картки. ✅
- **FR-8.2:** Усі типи зберігаються в БД; форма-модалка адаптується під тип; тост-підтвердження. ✅
- **FR-8.3 [Фаза 2]:** Нотифікація менеджеру (email/Telegram) при новій заявці.
- **FR-8.4:** Anti-spam (rate limit, honeypot/captcha).

### 3.10 Блог (P13, P14)
- **FR-9.1:** Список статей з пагінацією, прев'ю-зображенням, датою, автором, категорією.
- **FR-9.2:** Сторінка статті з контентом, мета-даними, OG.
- **FR-9.3:** Категорії/теги постів.

### 3.11 Футер (наскрізний)
- **FR-F1:** Логотип.
- **FR-F2:** Лінки: Обмін та повернення, Доставка та оплата, Політика конфіденційності, Договір оферти.
- **FR-F3:** Контакти: місто, телефон (tel:), email.
- **FR-F4:** Логотипи платіжних систем.
- **FR-F5:** Меню: Магазин, Про нас, Контакти. Кнопка «Наверх».

## 4. Адмін-панель (FR-A)

> **Архітектура (ADR-0004):** адмінка — **окремий Next.js застосунок** (`tesla-admin`), що споживає той самий NestJS API. Доступ — за роллю в JWT (RBAC на рівні API).

- **FR-A1:** Авторизація та ролі: **User** (покупець), **Admin** (керування каталогом/замовленнями/контентом), **SuperAdmin** (+ керування адмінами/ролями та системними налаштуваннями).
- **FR-A2:** CRUD товарів: назва, артикул, ціна/стара ціна, стан, тип, наявність, **категорія**, **сумісність (вибір авто з довідника, M2M)**, зображення (завантаження в S3) — **окремо галерея та «живі фото»** (`isLive`, FR-3.1a), опис, характеристики.
- **FR-A3:** CRUD категорій (глобальне дерево) та **довідника авто** (`cars`: моделі/покоління/дати).
- **FR-A4:** Управління замовленнями: перегляд, зміна статусу замовлення та **статусу оплати**, фільтрація за статусом і **статусом оплати**, **пошук за номером/телефоном/email** ([ADR-0013](adr/0013-order-status-method-columns.md)).
- **FR-A5:** Розділ **«Ліди»** — у сайдбарі **акордеон** із під-сторінками за типом: **Підбір** (`fitment`), **«Знайшли дешевше»** (`price_match`), **Підписка на ціну** (`price_subscribe`), **Контакт / 1 клік** (`contact`). Кожен тип — власна сторінка зі списком/фільтрами й статусом (`new → handled`).
- **FR-A5a [НОВЕ]:** Під тим самим розділом — під-сторінка **«Обране (лайки)»**: хто додав товар в обране, **контакт для дзвінка**, товар і дата; лічильник/сортування за популярністю товару, фільтр за товаром/клієнтом. Джерело — модель `WishlistItem` (не таблиця `leads`), подається як сигнал інтересу ([ADR-0012](adr/0012-wishlist-auth-crm.md)).
- **FR-A6:** CRUD блогу.
- **FR-A7:** Управління банерами головної.
- **FR-A8:** Масовий імпорт/експорт товарів (CSV/JSON) — для міграції з WooCommerce.
- **FR-A9 [НОВЕ]:** Розділ **«Налаштування»** (superadmin) — системні інтеграції. Секція **«Нова Пошта»**: статус довідника (к-сть міст/відділень, час останньої синхронізації, стан) і кнопка **ручного запуску синхронізації** ([ADR-0014](adr/0014-nova-poshta-directory-mirror.md)). Авто-синхронізація — cron раз на 2 тижні (`RUN_CRON`); на тесті `RUN_CRON=false`, тож синк — кнопкою.

## 6. Моделі даних (PostgreSQL, орієнтовна схема)

> **Канонічна схема — у [db-schema.md](db-schema.md) (Prisma).** Нижче — оглядові визначення; за розбіжностей джерело істини — Prisma-схема.
>
> Ключова зміна (ADR-0002): **сумісність відокремлено від таксономії**. Товар — один запис; модель авто — через довідник `cars` і M2M-таблицю `product_fitment`; категорії — глобальний довідник.

### cars — довідник автомобілів (рівень покоління/фейсліфта)
```
cars(
  id PK,
  brand            text,                 -- Tesla
  model            text,                 -- Model 3 / Model Y / Model S / Model X
  generation       text,                 -- Pre-facelift / Highland / Phase 1 / Juniper
  slug             text unique,          -- model-3-highland
  production_start date,
  production_end   date null             -- null = у виробництві
)
```

### categories — глобальний довідник категорій деталей (спільний для всіх моделей)
```
categories(
  id PK, slug unique, name,              -- kuzov / «Кузов»  (ПЛОСКИЙ список, без ієрархії)
  sort_order int, seo jsonb
)
```

### products — товар (один запис, унікальний артикул)
```
products(
  id PK, slug unique, name,
  sku           text unique,             -- артикул / код запчастини
  price         numeric, old_price numeric null,
  on_sale       boolean,                 -- знижка активна (показ старої ціни)
  condition     text default 'new',
  type          text,                    -- 'original' | 'analog'
  stock_qty     int,                     -- наявність = stock_qty > 0 (без окремого in_stock)
  category_id   FK → categories.id,      -- одна категорія
  attributes    jsonb,                   -- гнучкі характеристики (ключ-значення)
  description_json/html,                 -- rich text (ADR-0006)
  seo           jsonb,                   -- { title, description, ogImage }
  created_at, updated_at
)
-- Гарантія/доставка — НЕ тут, а у content_blocks (ADR-0009)
```

### content_blocks — наскрізні тексти (ADR-0009)
```
content_blocks(
  id PK, key unique,                     -- warranty | delivery_payment
  title, body_json/html                  -- rich text
)
```

### payment_requisites — реквізити продавця (ADR-0008, superadmin)
```
payment_requisites(
  id PK, label,                          -- ПІБ отримувача (3 слова)
  tax_id, iban, bank_name,
  liqpay_public_key, liqpay_private_key, -- зашифровано (AES-GCM)
  monopay_token,                         -- токен monobank, зашифровано
  iban_active, liqpay_active, monopay_active -- канали; активний один на канал
)
```

### product_fitment — M2M сумісність товар ↔ авто
```
product_fitment(
  product_id FK → products.id,
  car_id     FK → cars.id,
  year_from  int null, year_to int null, -- уточнення в межах покоління (опц.)
  PRIMARY KEY (product_id, car_id)
)
```

### product_images / related
```
product_images(id PK, product_id FK, url, alt, sort_order)   -- S3 URLs
product_related(product_id FK, related_id FK → products.id, PK(product_id, related_id))
```

### orders / order_items
```
orders(
  id PK, order_number text unique, user_id FK null,          -- null для гостя
  customer jsonb,                          -- снапшот { name, phone, email }
  delivery jsonb,                          -- снапшот { city, warehouse }
  delivery_method text,                    -- np|ukrposhta|pickup (ADR-0013)
  payment_method  text,                    -- card|cod|iban|cash (ADR-0013)
  payment_status  text,                    -- pending|paid|failed|refunded (ADR-0013), індекс
  payment_invoice_id text null,            -- ID інвойсу monopay для звірки/вебхука (ADR-0015), індекс
  total numeric, status text,              -- new|processing|shipped|done|canceled
  is_one_click boolean, comment text, created_at
)
-- пошук за контактом: trigram GIN на (customer->>'phone') / (customer->>'email')
order_items(id PK, order_id FK, product_id FK, name, sku, price, qty)
```

### users / addresses
```
users(id PK, email unique, phone, password_hash, first_name, last_name, role, created_at)
addresses(id PK, user_id FK, label, method, city, warehouse, recipient)
```

### leads
```
leads(
  id PK, type text,                        -- fitment|price_match|price_subscribe|contact
  name, phone, email null, vin null, link null,
  target_price numeric null, product_id FK null, message null,
  status text default 'new', created_at
)
```

### blog_posts
```
blog_posts(id PK, slug unique, title, excerpt, content, cover_image, author, category, published_at, seo jsonb)
```

> Запит «товари для авто X»: `products JOIN product_fitment ON … WHERE car_id = :id [AND system_id = :sys]`. VIN-підбір (Фаза 3): VIN → `cars` → сумісні товари.

## 7. Нефункціональні вимоги (деталізація)

- **NFR-1 (Performance):** ISR з ревалідацією для каталогу/товарів; оптимізація зображень (next/image + S3/CDN, webp/avif); LCP < 2.5с.
- **NFR-2 (SEO):** SSR/ISR, унікальні meta/OG/canonical на сторінку, JSON-LD (Product, BreadcrumbList, Organization), `sitemap.xml`, `robots.txt`.
- **NFR-3 (Міграція URL):** карта 301-редиректів зі старих WooCommerce URL (`/product/...`, `/product-category/...`) на нові; зберегти slug-и де можливо. **Обсяг редиректів залежить від факту індексації чинного сайту** — див. [ADR-0001](adr/0001-url-structure-and-redirects.md) та [SEO-стратегію §2.1](seo-strategy.md#21-url-і-редиректи) (якщо сайт не проіндексований — карта 301 не потрібна).
- **NFR-4 (Адаптивність):** mobile-first, breakpoints, тач-жести в галереї.
- **NFR-5 (A11y):** WCAG 2.1 AA — alt-тексти, контраст, фокус, семантика.
- **NFR-6 (Security):** HTTPS, хешування паролів (bcrypt/argon2), JWT + refresh, валідація (class-validator), rate limiting, CORS, anti-spam на формах.
- **NFR-7 (Аналітика):** GA4 / інша система, події (add_to_cart, **add_to_wishlist**, begin_checkout, purchase, lead).
- **NFR-8 (i18n-ready):** структура під майбутню багатомовність (наразі UA).
